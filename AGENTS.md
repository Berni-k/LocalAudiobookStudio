# Agent instructions

Guidance for AI coding agents (and humans) working on Local Audiobook Studio. User-facing documentation is in
[README.md](README.md) and [docs/](docs).

## What this is

A desktop app (C#, .NET 10, Avalonia) that turns books into audiobooks with local AI voices. Text is imported into
a project of chapters and segments; each segment is generated by a *worker* (a model in its own process) and can be
edited, regenerated and mixed. `las` is the command line for the same engine.

## Layout and dependencies

| Project | Contains | May depend on |
|---|---|---|
| `src/LocalAudiobookStudio.Core` | Project model, text import, timeline, settings, hashing | nothing |
| `src/LocalAudiobookStudio.Audio` | Decoding (WAV, Opus with Concentus, MP3 with NLayer), Opus encoding, mixing, loudness, peaks (no devices) | Core |
| `src/LocalAudiobookStudio.Workers` | Worker processes and protocol, scheduler, Python environments (uv) | Core |
| `src/LocalAudiobookStudio.Engine` | Everything without a UI: `StudioHost`, `ProjectEngine`, `HeadlessProject`, export, one-off jobs, system checks, tool downloads | Core, Audio, Workers |
| `src/LocalAudiobookStudio.App` | Avalonia UI: views, view models, `ProjectSession`, playback and recording (`Devices/`) | Engine |
| `src/LocalAudiobookStudio.Cli` | `las` | Engine |
| `src/LocalAudiobookStudio.HartsyWorker` | `las-hartsy-worker`, a standalone worker on HartsyInference | nothing in this repo (its DLLs must not mix with the app's) |
| `src/LocalAudiobookStudio.InternalWorker` | `las-internal-worker`, a standalone worker for engines that run in .NET: Whisper.net / whisper.cpp, ONNX Runtime on the CPU (published as one file into `tools/internal-worker/`; links the Hartsy worker's `Protocol.cs`) | nothing in this repo |
| `workers/` | Worker manifests, Python workers, `environments.json` | – |
| `tests/LocalAudiobookStudio.Tests` | Unit tests | Engine |

Rules that follow from this:
- No Avalonia, UI thread or view models below the App. Logic both the app and `las` need belongs in the Engine;
  the App's `AppHost` and `ProjectSession` forward to `StudioHost` and `ProjectEngine`.
- `ProjectSession` lives on the UI thread. `ProjectEngine` isn't thread-safe; only `SaveGeneratedTake` runs on
  scheduler threads.

## Build, run, test

- Build and run: open `LocalAudiobookStudio.sln` and run, or `dotnet run --project src/LocalAudiobookStudio.App`
  (`run.bat` / `run.sh`).
- Compile check while the app may be running (it locks its `bin` folder): build into a temporary folder,
  `dotnet build src/LocalAudiobookStudio.App -o <temp dir>`, and delete it afterwards. Building the App also builds
  `las` and publishes the HartsyInference worker into `tools/hartsy/` and the internal worker into `tools/internal-worker/`.
- Tests: `dotnet test`. They must run without GPUs, installed workers or network. Integration tests against real
  workers were removed on purpose (too dependent on the machine's state); check real workers with `las` instead.
- The GUI is tested by the maintainer. Don't launch or drive the desktop app to verify a change; compile-check and
  describe what to look at.
- Release: bump `<Version>` in `Directory.Build.props` in the release commit, then push a tag `vX.Y.Z`; the release
  workflow builds zips with `build/release.ps1` and creates a draft GitHub release.

## Checking things with `las`

`las` sits next to the app in the build output and uses the app's settings, installed workers and data folder.

- `las doctor` (system check), `las workers`, `las workers <id>` (settings and voices), `las devices`
- `las workers install <id>` (also `repair`, `uninstall`; `--runtime <name>`): what the Workers window does, so a new
  worker can be installed and tried without the GUI
- `las tts "Hello" -o out.wav -w test_tone`: a quick pipeline check without a model download (install *Test tones*
  once with `las workers install test_tone`; it only needs NumPy)
- `las project <dir> import book.txt generate export -o book.m4b`: a whole project headless
- `las transcribe out.wav -t "Hello" --words`: what a transcription worker hears, word timings, differences from the text
- `--json` for machine-readable output. Exit codes: 0 ok, 1 failures, 2 usage, 3 setup needed, 130 cancelled.
- A project can't be open in the app and in `las` at the same time (`.cache/open.lock`).

## Conventions

- C#: .NET 10, nullable on, file-scoped namespaces, 4-space indent. Primary constructors and collection expressions
  are fine. XAML: compiled bindings (every view and data template sets `x:DataType`), 2-space indent.
- MVVM with CommunityToolkit.Mvvm (`[ObservableProperty]`, `[RelayCommand]`). Edits to a project go through
  `ProjectSession` so they are undoable and saved.
- Comments and XML doc comments explain *why*, in plain English, at the density of the surrounding code.
- User-facing text: short, plain sentences. Say what happened and what to do next.
- Package versions live in `Directory.Packages.props` (central package management); `.csproj` files have none.
- A segment of a kind the app doesn't know (from a newer version) loads as `ItemKind.Unknown`, shows its raw JSON and
  is saved back unchanged (`TimelineItemConverter`). A new kind only needs its `[JsonStringEnumMemberName]`.
- The app isn't released yet: don't keep backwards compatibility. Remove old fields and features outright; no
  migrations, legacy read paths or project format bumps for them.

## Workers

- Each worker is a folder in `workers/` with a `manifest.json`. Runtime variants are overlays
  (`manifest.python.json`, `manifest.onnx.json`, `manifest.hartsy.json`, …) that replace top-level fields;
  `runtimeOrder` picks the default.
- Python workers run in shared environments defined in `workers/environments.json` (named
  `torch<major>_<minor>-<cuda>-tx<transformers major>`, `onnx…`, `basic`). A manifest only sets `envGroup`.
- A Python worker implements `load(report)` and `generate(req, report)` (optionally `prepare(report)` for downloads)
  with `workers/common/protocol.py`. Stdout carries protocol messages only; everything else goes to stderr.
- A model's `modelVersion` is part of every segment's input hash: changing it makes all its takes stale.
- Settings can come from a file: a setting with `"addsSettings": "<reader>"` (usually `"type": "asset"`) picks a file,
  and the reader in `SettingSources.cs` turns it into more settings shown below it. The ComfyUI bridge's workflow
  (`comfyWorkflow`) is the first; add a reader there for other kinds of file.

## Models

- Workers never download models themselves. Every model is an entry in `workers/models.json` (sources pinned to a
  commit, every file with its size and hash); a worker asks the app for it by id when it needs it (`needModel`),
  and the app's `ModelStore` downloads it into `models/store/<id>`, checks it and replies with the folder.
  Nothing is downloaded ahead of time; requests are served one at a time.
- Python: `ensure_model("kokoro-82m")` returns the folder; `model_file(id, "voices/x.pt")` fetches an extra file
  (voices) that models.json doesn't list. Load from the folder, never by repo id: Python workers run with
  `HF_HUB_OFFLINE=1`, so a library fetching by repo id fails.
- HartsyInference: the worker asks for its models with `linkTo` (HartsyInference's own folder,
  `AudioModelCache.GetRepoDirectory`) or single-file `links`; the app makes that folder a junction to the store
  folder (single files: hard links). HartsyInference finds the files there and downloads nothing, and what it
  writes there (converted weights) lands in the store. The mapping is in `ModelLinks.cs`.
- A manifest's `models` lists the ids it may ask for (shown and deleted in the Workers window).
- Adding a model or moving its revision: edit `sources` (and `include` to pick files), then
  `las models pin <id> --file workers/models.json` fills in `files`. Large files get a SHA-256, small ones the
  Hub's git hash (so gated repos pin without a token).
- Users can point a model at their own folder (Workers window); that becomes part of the input hash.

## Adding a worker

1. **Model files**: add an entry to `workers/models.json` (`displayName`, `sources` with `repo` and a commit
   `revision`, `include` globs), then run `las models pin <id> --file workers/models.json` to fill in `files`.
2. **Folder**: `workers/<id>/` with `manifest.json`, `worker.py`, `requirements.txt` and a short `README.md`
   (backend, what the settings do, quirks). Copy the closest existing worker: `kokoro` (built-in voices, CPU too),
   `qwen3_tts` (voice cloning), `stable_audio_3` (sound effects with a length), `test_tone` (the bare minimum).
3. **Manifest** essentials:
   - `id`, `displayName`, `description`, `tags` (`Voice`, `Voice clone`, `SFX`, `Music`…), `priority`.
   - There is no worker kind: speech, sounds and music are all speaker segments, and the request's `text` is spoken or
     describes the sound. What differs is declared: `length`: `{ "mode": "none|optional|required", "min", "max" }`
     (default none), `voiceCloning`, and on HartsyInference `hartsyModality: "music"` for its music catalog.
   - `envGroup` (an environment in `environments.json`; reuse one, or add one if the pins clash), `modelVersion`,
     `models` (the models.json ids it asks for), `maxChars`, `sampleRate`, `voiceCloning`, `approxVramGb`,
     `devices` (`["cuda"]`, `["cuda", "cpu"]`; `cpuRecommended: false` for slow CPU runs).
   - A worker tagged `Transcription` (hears words, with timings) or `Alignment` (finds a known text's words in audio)
     listens instead of generating: it implements `transcribe(req, report)` instead of `generate`, gets a 16 kHz mono
     WAV (`req.audio_path`) and the expected text (`req.text`), and isn't offered as a speaker's voice. A language
     is an ordinary `language` enum setting (`Auto` plus codes, read from `req.settings`), as in `whisper`; a model
     that detects the language itself has none. Copy `parakeet`.
   - `settings`: per speaker, overridable per segment. Types: `float`, `int`, `bool`, `string`, `enum` (`options`,
     `optionLabels`), `seed`, `file`, `asset` (`extensions`; `addsSettings` to read more settings from the file).
     A `voice` enum setting holds built-in voices. `workerSettings` are per machine (servers, tokens).
4. **worker.py**: a class with `load(report)` and `generate(req, report)` (optionally `prepare(report)` and
   `selftest()`), run by `run_worker(...)` from `workers/common/protocol.py`. Get model folders with
   `ensure_model(id)`, write `req.out_path` with `write_wav`, and return
   `{"durationMs", "seed", "sampleRate"}`. In `generate`, call `report(fraction, message)` often: it also raises when
   the job is cancelled. Use `torch_device()` so the CPU slot works.
5. **Other runtimes** (optional): `manifest.<runtime>.json` overlays (`onnx`, `onnx-cuda`, `hartsy`, `internal`,
   `internal-gpu`) next to it; mark settings a runtime can't do with `unsupportedSettings` / `unsupportedOptions`.
   - `internal` runs the model in .NET on the bundled `las-internal-worker`, no Python: the manifest names an `engine`
     (`whisper`: ggml Whisper models on whisper.cpp; `tdt`: NeMo TDT transducers on ONNX Runtime, CPU) and an
     `engineConfig` mapping each value of a worker setting (`modelSetting`) to a models.json id and the engine's files.
     A new model of a kind an engine knows needs only that (see `whisper`, `parakeet`); a new kind is a class in
     `src/LocalAudiobookStudio.InternalWorker` (derive from `EngineBase`, register in `Engines.cs`, add the name to
     `InternalGpuRuntime.Engines`). Transcribers send their words through `TranscriptWords` (open ends, overlaps, and
     for models that invent text over silence, the silence check).
   - `internal-gpu`: the same with the engine's GPU builds, downloaded on install and pinned in `InternalGpuRuntime.cs`
     (whisper: Vulkan, and the CUDA 12 or 13 build matching the user's toolkit; cudart and cuBLAS come from that
     toolkit on the PATH, as for HartsyInference). Moving Whisper.net to a new version means new hashes there too.
6. **Docs**: add the model to the table in `docs/models.md` (task, devices, license, links).
7. **Check**: `dotnet test` catches manifest and models.json errors. Then install the worker in the Workers window
   and try it with `las workers <id>` and `las tts "Hello" -o out.wav -w <id> -v` (worker log on stderr).

## Audio files

- Workers always write WAV. The app analyses it (loudness, trims, peaks), then stores it in the project's format
  (`ProjectDefaults.AudioFormat`, Opus by default, at `ProjectDefaults.OpusKbps` per channel; `ProjectEngine.StoreAudio`). `TakeInfo.Format` says which;
  use `ProjectPaths.TakeAudio` / `TakeIndex.TakeAudio`, never assume `.wav`.
- `AudioDecoder.Decode` reads WAV, Opus and MP3 by extension; everything after it (cache, resampling, mixing,
  export) is format-free. Opus files are written and read by our own `OggOpus` (Ogg container with the real
  pre-skip and exact end), so takes keep sample-accurate timing; don't swap in Concentus.OggFile, which doesn't.

## Hard-won fixes (don't regress)

- The worker stdin reader on Windows uses `PeekNamedPipe` before reading; a blocking `ReadFile` deadlocks against
  DLL loads (NumPy, torch). See `_stdin_lines` in `workers/common/protocol.py`.
- The C# side writes worker stdin through a BOM-free `StreamWriter`; the Python side also strips a BOM.
- torch is pinned with its local tag (`torch==2.11.0+cu128` in `environments.json`); otherwise uv picks PyPI's
  CPU-only build.
- `LAS_DEBUG_HANG=<seconds>` makes a Python worker dump all thread stacks to its log.
